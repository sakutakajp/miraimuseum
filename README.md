# みらい博物館 / MIRAI MUSEUM

さまざまな「展示テーマ」と「ゲームジャンル」を組み合わせ、短いゲームを次々に遊べるWeb上の博物館。

恐竜、宇宙、深海、人体、数学、歴史、ロボットなどのテーマを、横スクロールアクション、シューティング、パズル、クイズなど異なる遊び方で体験する。ゲームごとに2D、2.5D、3D、ドット絵、イラストなど表現方法も変えてよい。

最優先するのは「教育ゲームにすること」ではなく、ゲームそのものを面白くすること。学問や知識はゲームの題材として扱い、遊んだ結果として興味が生まれることを狙う。

## ランディングページ / ブランド体験の新方針

2026-10-06以降、トップページと「みらい博物館」ブランド体験では、**「子ども向け」をアートディレクション上の判断軸から外す**。年齢を問わず初見で触りたくなる、国際的なデジタル・エクスペリエンス水準を狙う。

North Starは「インターネット上に存在する、まだ誰も見たことがない博物館」。ブランドステートメントは **EVERYTHING IS CONNECTED. / すべての学問は、つながっている。**

実装・デザイン判断では次の仕様を一次資料とする。

- [Landing Page Experience Specification](docs/landing-page-experience.md) — 全体の体験、アートディレクション、Scene 00〜08、性能・アクセシビリティ方針
- [Landing Page Scenes 00–02 Implementation Specification](docs/landing-page-scenes-00-02.md) — 最初の520vhを実装するPhase 1仕様
- [DEEP TIME Stage 1 詳細実装仕様](docs/dinosaur-stage1.md) — 恐竜2Dランナーを高難度シネマティック・リズムアクションへ再設計する一次仕様
- [STAR DIVE Stage 1 詳細実装仕様](docs/star-dive-stage1.md) — Featured Exhibitにもなる宇宙3Dゲームの実装仕様

ゲーム操作についての「子どもでも直感的に理解できる」「スマートフォン縦画面を第一級にする」という要件は維持する。ただし、それを幼児向けの色・イラスト・カードUIに結び付けない。

## 現在の実装と次のMVP

2026-10-05時点のコードには、Nuxt + Phaser + TypeScriptで作った恐竜の横スクロールプロトタイプが1ステージ実装されている。

今回の再設計では、この実装を「みらい博物館に収録される1作品」と位置付け直す。最終的に恐竜だけを拡張するのではなく、性質の大きく異なるゲームを同じ博物館に追加できる構造へ移行する。

次のMVPで実装する範囲:

- みらい博物館本体
- 「今日のおすすめ」
- 「展示テーマから選ぶ」
- 「あそびかたから選ぶ」
- ゲーム詳細画面
- ステージ選択
- 恐竜 × 2D横スクロールアクション: Stage 1
- 宇宙 × 3Dシューティング: Stage 1
- ステージ進行とハイスコアの端末保存

まず2本を1ステージずつ実装し、2Dと3Dという異なるゲームを同じ博物館に共存させられることを検証する。検証後、両ゲームを5ステージまで増やす。

### 現在のプロトタイプを動かす

    npm ci
    npm run dev

Node.jsは22.19以上の22系、24.11以上の24系、または26以上を使う。開発サーバーはポート3000で起動する。

現在の恐竜プロトタイプは、スマートフォンではタップ、PCではクリック・Space・↑でジャンプする。ⅡボタンまたはEscで一時停止でき、ページが非表示になると自動で一時停止する。

現在の実装には、約80秒の恐竜ステージ、6種類の発見、博物館への展示、localStorageへの保存など、旧仕様に基づく機能も残っている。これらはV2のMVPへ移行する際に再評価する。

### VS CodeのDev Containerでデバッグ

Docker Desktop（LinuxはDocker Engine）、VS CodeのDev Containers拡張、ホスト側のChromeまたはEdgeを用意する。ホスト側へのNode.jsのインストールは不要。

1. このリポジトリをVS Codeで開き、Dev Containers: Reopen in Containerを実行する。
2. 初回はNode.js 24のコンテナをビルドし、npm ciを自動実行する。
3. 「実行とデバッグ」でMIRAI: ChromeまたはMIRAI: Edgeを選び、F5を押す。
4. ゲームロジックは app/game 以下、Vue側は app 以下でデバッグする。

コンテナのポート3000をホストの3000へ転送する。ブラウザーテストはコンテナ内で npm run test:e2e を実行できる。

### 検証と本番起動

    npm test
    npm run typecheck
    npm run build
    npm run preview
    npm run test:e2e

現在のテストには旧恐竜プロトタイプを前提とするものが含まれる。V2実装時に、博物館本体、ゲーム選択、スコア、ステージ解放、2D/3Dゲーム起動を検証するテストへ拡張する。

## 1. V2コンセプト

「みらい博物館」は単一ジャンルのゲームではなく、多数の小さなゲームを収録できる器とする。

ゲームの基本構造は次の3軸で考える。

**展示テーマ × ゲームジャンル × 表現方法**

例:

| 展示テーマ | ゲームジャンル | 表現 |
| --- | --- | --- |
| 恐竜 | 横スクロールアクション | 2D / ドット絵 |
| 恐竜 | シューティング | 2D / 3D |
| 宇宙 | シューティング | 3D |
| 深海 | 探索 | 2.5D / 3D |
| 数学 | パズル | 2D |
| 人体 | 探索 | 3D |
| 歴史 | アドベンチャー | イラスト |

同じ「テーマ × ジャンル」の組み合わせに複数作品を置いてよい。たとえば「恐竜 × シューティング」でも、やさしい作品、難しい作品、ボス戦中心の作品を別々に作れる。

難易度として変化させたいのは、主にゲームとしての難しさ。学習内容の難易度とは分離する。

## 2. プレイヤーと対象

- 子どもが直感的に遊べることを基準にする。
- デザインを幼児向けに固定せず、高難度ゲームやハイスコア挑戦は大人でも楽しめるようにする。
- 学習を必須にしない。ゲームとしての面白さを最優先する。
- 学問や知識は題材として使う。明示的な解説やクイズを全作品へ強制しない。

## 3. 博物館のナビゲーション

MVPでは博物館内をキャラクターで歩き回らない。ゲーム一覧・詳細画面を使ってすぐ遊べる構造にする。

将来は博物館内を歩き、展示に入る方式へ発展させられる。

### トップ画面

トップには「今日のおすすめ」を1作品、大きく表示する。

その下から2つの軸でゲームを探せる。

- **展示テーマから選ぶ**: 恐竜、宇宙、深海、人体、ロボットなど
- **あそびかたから選ぶ**: アクション、シューティング、パズル、クイズなど

「ゲームジャンル」という語を子ども向けUIでそのまま使う必要はない。「あそびかた」のような分かりやすい表現を優先する。

同じゲームへ、テーマ側からもジャンル側からも到達できる。

### ゲーム開始まで

1. トップまたは一覧からゲームを選ぶ
2. ゲーム詳細画面を開く
3. ステージを選ぶ
4. 数秒の操作デモを見る
5. プレイ開始

ゲーム詳細画面は共通レイアウトを使う。ただし背景、色、イラスト、3Dモデルなどは各ゲームの世界観に合わせて変える。

## 4. 共通するゲームデザイン

すべての作品を同じルールにするのではなく、「入りやすさ」と「短時間で遊べること」を共通化する。

### 画面と入力

- 基準端末はスマートフォン縦画面。
- タップ、長押し、スワイプ、ドラッグを使える。
- 原則としてタッチ操作中心で設計する。
- 仮想十字キーや多数の画面ボタンを前提にしない。
- PC対応は可能だが、ゲームデザインの基準はスマートフォン縦画面。

### 操作説明

各ゲームの初回プレイ時は、文章による長い説明を出さない。

指のアニメーションなどで、タップ、スワイプ、ドラッグといった必要な操作を数秒だけ見せ、すぐプレイへ移る。

### ステージ

- 1ステージは原則30秒〜1分程度。ただし作品の体験設計を優先し、必要なら約90秒まで使う。宇宙シューティングStage 1は約80秒。
- ステージ数はゲームごとに自由。
- Stage 1をクリアするとStage 2が開く、という順次解放を基本とする。
- 後半ほど難しくする。
- 数値だけを難しくするのではなく、新しい敵、ギミック、環境など「違う体験」を追加する。
- 失敗条件、ゲームオーバー、リトライ方式はゲームごとに設計する。

## 5. スコアと進行

原則として各ゲームにスコアを持たせる。ただし採点方法はゲーム内容に合わせる。

例:

- シューティング: 撃破数、命中、コンボ
- クイズ: 正解数、回答速度
- レース: タイム
- パズル: 手数、時間
- アクション: アイテム、到達、ノーミスなど

保存する記録:

- 各ステージのベストスコア
- ゲーム全体のベストスコア
- 解放済みステージ
- クリア進行状況

ゲーム一覧には進行状況と自己ベストを表示する。

MVPではログインを設けず、ブラウザーの端末保存を使う。将来、オンラインランキングへ拡張できるようにする。

現時点では、共通コイン、共通通貨、図鑑、発見コレクションなど、博物館全体をまたぐメタゲームは設けない。

## 6. 主人公

- 全ゲームで同じ主人公を使う。
- 主人公の具体的なキャラクターデザインは未決定。
- ゲームのテイストに合わせ、同じ主人公自身の表現も変える。

例:

- ドット絵ゲームではドット絵
- 3Dゲームでは3Dモデル
- 絵本風ゲームでは手描き・イラスト表現

「同じ主人公が、まったく異なる展示世界へ入る」ことを作品全体のつながりとして使う。

## 7. ビジュアル

### みらい博物館本体

トップページと博物館ブランドシェルの一次仕様は **[Landing Page Experience Specification](docs/landing-page-experience.md)** とする。基本アートディレクションは「Quiet Museum / Impossible Exhibits」。静かな美術館・自然史博物館の質感を土台に、現実では同じ空間に存在しない展示が侵入する。旧方針の「明るくカラフルで、少し未来感」は共通スタイルとしては採用しない。

### 各ゲーム

各ゲームの表現方法は自由。

- 2D
- ドット絵
- 2.5D
- 3D
- イラスト
- リアル寄り
- その他、そのゲームに適した表現

ゲーム部分まで博物館UIの見た目へ統一しない。作品ごとに世界観を大きく変えられること自体を「みらい博物館」の特徴にする。

## 8. 最初のゲームA: 恐竜 × 2D横スクロール

Stage 1は旧プロトタイプの延長ではなく、**MIRAI: DEEP TIME — CRETACEOUS // LAST DAY** として全面的に再設計する。

実装時は、このREADMEの一般方針や旧プロトタイプ挙動より **[DEEP TIME Stage 1 詳細実装仕様](docs/dinosaur-stage1.md)** を優先する。

### Stage 1の基本

- Phaser 3による2D横スクロールアクション。
- 自動前進 + タップ / Space / ↑ の1入力ジャンプ。
- 一撃死。衝突後の巻き戻し、無敵時間、3回失敗後の自動救済は廃止する。
- 死亡から約900ms以内の高速リトライを目標とする。
- 150 BPM / 48小節 / 約76.8秒を、CALM → HERD → PREDATOR → FLASH → FALLOUT → BOUNDARYの6 sectionで構成する。
- 音楽、障害物、恐竜、カメラ、VFXを共通StageClockで同期する。
- ゲームプレイは1/240秒のfixed timestepを基準とし、描画フレームレートで難易度が変わらない決定論的挙動を目指す。
- 旧ピクセルアートを最終表現にせず、Editorial Paleontology × Motion Graphicsのアートディレクションへ刷新する。
- プレイ中のDiscovery Toastは廃止し、知識はタイポグラフィや地層表現として世界へ埋め込む。詳しい展示はクリア後にOPEN EXHIBITから開く。

### Stage 1の記録

- 失敗runではBEST到達率を主要記録にする。
- clear時にSYNC精度を含む最大100,000のRUN SCOREとRankを確定する。
- best progress、best clear score、best sync、best rank、clear statusを端末保存する。
- 機能数より、jump feel、death/retry、音楽同期、camera、T. rex演出、K–Pg境界endingの完成度を優先する。

### 5ステージの方向性

各ステージで、背景だけを差し替えるのではなく、環境・恐竜・ギミックをまとめて変える。後半になるほど新しい体験と難しさを増やす。

具体的な5ステージの内容は今後決定する。

## 9. 最初のゲームB: 宇宙 × 3Dシューティング

恐竜ゲームと同時にV2の構造を検証するための2本目。

Stage 1は、単純な敵ウェーブ型シューティングではなく、映像・カメラ・音・入力・スコアを約80秒の振付として一体化する `MIRAI: STAR DIVE — ASTEROID BELT` として制作する。実装時は、この節の概要よりも **[STAR DIVE Stage 1 詳細実装仕様](docs/star-dive-stage1.md)** を優先する。

### 基本ルール

- 3Dシューティング。
- 宇宙船の後方から見る視点。
- スマートフォン縦画面。
- 指をドラッグすると宇宙船が上下左右に移動する。
- 射撃は自動。
- 全5ステージ構想。
- Stage 1は約80秒。144 BPM / 48小節を6つのsectionに分けて演出とゲーム進行を同期する。
- Stage 1から順番に解放する。
- 後半ほど新しい敵、障害物、ギミックを増やして難しくする。
- 障害物の近くをノーダメージで通過する `NEAR` と、その連続成功による `RISK` 倍率をStage 1の特徴にする。

### シールドと失敗

- シールドは3。
- 3回ダメージを受けるとステージ失敗。

### スコア

Stage 1ではターゲット破壊、`CHAIN`、`NEAR / RISK` を中心にする。残りシールドはクリアボーナスとし、レール進行のためクリアタイムは採点対象にしない。

3Dレンダリングは **Three.js + TresJS** を採用する。Nuxt/Vueとの統合にはTresJSを使い、Three.jsの3Dシーン、カメラ、レンダリング機能を利用する。MVPでは3D物理エンジンを追加せず、宇宙船・隕石・敵などの当たり判定はシンプルな距離判定やBounding Box判定で実装する。

## 10. 技術方針

現在の実装:

- Nuxt: サイト、博物館UI、画面遷移
- Phaser: 2Dゲーム（現在の恐竜ゲームを含む）
- Three.js + TresJS: 3Dゲーム（宇宙3Dシューティングから採用）
- TypeScript: アプリとゲームロジック
- localStorage: 現在の端末保存

V2では、Nuxtを「みらい博物館」の共通シェルとして維持し、ゲームごとに適したゲーム実装を載せられる構造へ変更する。

2Dゲームは現在のPhaser資産を活用する。3DゲームはThree.js + TresJSを使う。PhaserとThree.jsを1つのゲームエンジンとして混在させず、博物館側から共通のゲーム起動・終了・スコア・進行インターフェースを介して各ゲームを独立して扱う。

ゲーム固有のコードと、博物館側の共通情報を分離する。博物館側が最低限必要とするゲーム情報は次のようなものを想定する。

- game ID
- タイトル
- 展示テーマ
- ゲームジャンル / あそびかた
- ビジュアル
- ステージ一覧
- 進行状況
- ベストスコア
- ゲーム起動方法

これにより、新しいゲームを追加しても博物館本体を大きく書き換えない構造を目指す。

## 14. 既存プロトタイプからV2への移行

既存の恐竜プロトタイプは捨てず、最初の「恐竜 × 2D横スクロール」作品へ活用する。

ただし、旧仕様の以下の点はV2では全体共通ルールではない。

- 全ゲームが横スクロール
- 操作がタップジャンプだけ
- ゲームオーバーなし
- 発見収集が全体の中心
- 発見率を主要な進捗にする
- ピクセルアートで全体を統一
- 1〜2分の長いステージ
- 博物館展示の収集でゲーム全体を進める

既存コードは段階的にV2へ移行する。まず博物館シェルとゲーム登録構造を作り、既存恐竜ゲームを1作品として接続し、その後に宇宙3Dシューティングを追加する。

---

この仕様の目的は、ひとつのゲームを完成させることではなく、**異なるテーマ・ジャンル・表現のゲームを継続的に追加できる「みらい博物館」という器を作ること**にある。
