# MIRAI MUSEUM — Babylon.js / フル3D 共通仕様

更新日: 2026-10-09
状態: 共通基盤・ホーム・恐竜ランStage 1をBabylon.jsへ移行。残る10ゲームとモバイル実機検証は未実施。
対象ブランチ: work

## 1. 決定事項と優先順位

3D展示と11ゲームのゲーム空間は **Babylon.js + TypeScript** で制作する。Nuxt / Vueはサイト、ルーティング、メニュー、説明、HUDを担当する。ホームと恐竜ランStage 1は移行済み。残る10ゲームは個別に拡張する。

本書をエンジン選定・フル3D方針・11ゲーム構成の一次仕様とする。旧文書のPhaser、Three.js、TresJS、2Dゲーム採用指示や宇宙シューティングの開発中止記述より本書を優先する。旧文書のゲーム固有の操作感、音楽同期、保存、アクセシビリティ要件は、個別に変更するまで維持する。

現行コードはNuxt / Vue / Babylon.js。Phaser / Three.js / TresJS向けの旧コード・依存・設定・描画テストを整理した。GLB原本・音源・ライセンス・翻訳・保存データは維持する。過去の検証記録をBabylon.js版の検証済み証拠として扱わない。

## 2. 技術の役割

| 領域 | 採用方針 |
| --- | --- |
| サイト・画面UI | Nuxt / Vue |
| 3D展示・ゲーム描画 | Babylon.js |
| ルール・ステージ定義・進行 | TypeScript |
| 3D素材 | GLBを基本とし、モデル・素材・アニメーションを管理 |
| スマートフォンアプリ | Capacitorによる展開を想定。導入・実機検証は後続作業 |
| 物理演算 | ゲームに必要な範囲で採用。Havok等の追加は個別検証後に決定 |

フル3Dとは、プレイヤー・地形・障害物・ゲーム内オブジェクトを3D空間で描くことを指す。横視点、見下ろし、固定カメラも使用できる。HUDやメニューはDOMでよい。すべてのゲームに自由移動カメラや剛体シミュレーションを要求しない。

Babylon.jsはクライアント側で初期化し、SSR中にCanvasやブラウザAPIへアクセスしない。ゲーム内部の毎フレーム更新をVueのリアクティブ状態へ流さず、得点・開始・終了などの意味のあるイベントを通知する。

## 3. 確定した11ゲーム

対象時代は恐竜時代以後。地球はゲームを選ぶ中心の展示で、11ゲームとは別に扱う。

| 2 | 人類の狩猟を表すオブジェクト（マンモス等を想定） | 迷路での収集・回避と罠の設置を組み合わせた狩猟ゲーム |
| 3 | 農場 | 農場運営ミニゲーム |
| 4 | ロゼッタストーン | 暗号・解読ゲーム |
| 5 | 中世の城 | タワーディフェンス |
| 6 | 帆船 | 航海・探索ゲーム |
| 7 | 工場 | 生産・販売・設備投資でコインを増やす経営ゲーム |
| 8 | 車 | レーシングゲーム |

狩猟ゲームの操作・盤面は独自に設計する。農場・工場は短時間で開始から結果まで到達できる範囲に絞り、無期限の経営シミュレーションにしない。具体的な制限時間、マップ数、作物数、敵数は試作後に決める。

ロゼッタストーンの展示モデルは、ユーザー指定により欠けのない形状とする。史実の現物の形状とは区別して扱う。

## 4. ステージの制作方針

以下は初期実装の設計方針。全ゲーム共通の巨大な専用エディターを先に作らず、各ゲーム1つの短いステージで遊びを検証する。

### 部品・配置・ルールを分ける

- **部品**: 地面、岩、木、壁、建物、キャラクター等の再利用できる3Dモデル。
- **配置データ**: モデルID、位置、向き、サイズ、当たり判定、出現地点、ゴール、カメラ設定。
- **ルール**: 勝敗、得点、制限時間、敵の行動、収穫・生産サイクル等のTypeScriptコード。

ステージデータは型付きTypeScriptで始める。外部編集が必要になった段階でJSON等へ切り出し、読み込み時に検証する。表示用の細かいメッシュと当たり判定は分け、箱・球・カプセル等の簡単な形を使う。モデルの使い回しでファイル容量を抑える。描画負荷は表示数・材質数・影・テクスチャも含めて計測する。

### 制作手順

1. 箱や平面だけで短いステージを作る。操作、カメラ、勝敗を先に確認する。
2. 配置・ルールをデータ化し、リトライで同じ初期状態へ戻せるようにする。
3. 必要な部品をローポリモデルに差し替える。
4. 音、照明、演出、HUDを加える。
5. PC・スマートフォンで操作性、読み込み時間、描画負荷を確認する。
6. 配置・難易度・目標を変えて次のステージを作る。

ランやレースは道の区間を接続し、迷路・農場・タワーディフェンスはグリッドを基本にする。航海は海面と島・岩礁・目的地、シューティングは敵の出現パターン、クレーンとバトルは小さな固定空間、暗号ゲームは3D盤面と問題データを組み合わせる。各ジャンルで必要なデータ形式を持たせる。

まず恐竜ランの既存ステージをBabylon.jsへ移植し、入力・読み込み・一時停止・保存・終了処理の共通部分を検証する。既存の音楽同期、ジャンプの判定、得点、保存キーを不用意に変えない。その後、他ジャンルでも共通部分が使えることを確認する。

## 5. 素材と軽量化

上質なローポリの展示物を基本とする。ゲームで小さく表示しても形が読めるようにし、細部は省略する。地球は主役として展示物より細かい造形を許容する。

- GLBの縮尺・正面方向・原点を揃え、モデルごとの補正を定義に集約する。
- 不要なメッシュ、ボーン、アニメーション、過大なテクスチャを整理する。
- 共通素材を再利用し、静的な部品を多数置く場合はインスタンス化を検討する。
- 表示用モデルと衝突用形状を分離する。
- Meshy等の生成モデルも、そのまま性能要件を満たすと見なさず確認・軽量化する。
- モデルの出典とライセンスを保持する。

11展示物と地球だけで全ゲームの素材が足りるわけではない。地形・敵・道具・背景部品を各ゲームの試作後に洗い出す。総モデル数や一律のポリゴン上限は、この段階では確定しない。

## 6. 読み込みと実行時管理

- 各ゲームを独立ロードし、ホームで11ゲームすべてを一括ダウンロードしない。
- 先読みは選択・解放されたゲームに限定し、素材の所有者と解放タイミングを明確にする。
- ホームとゲームの移動で描画ループ、入力イベント、音声、Scene、GPUリソースが残らないようにする。
- 一時停止、タブ非表示、アプリのバックグラウンド移行から安全に復帰する。
- WebGL2を初期の描画基準とし、WebGPUは必須にしない。追加する場合は対応確認とフォールバックを検証する。
- 解像度・影・装飾密度を調整できる品質設定を用意する。
- 描画不能時には静止画・説明・再試行などを提示する。フル3Dゲームの2D代替版を必須にしない。
- キーボード、タッチ、safe area、日英表示、reduced motion、保存失敗時の継続を維持する。

Capacitor向けには端末へ配置できるWebアセットを生成する構成を用意する。Nuxtのサーバー実行環境をそのまま端末へ同梱する前提にしない。サーバー機能が必要ならAPIとして分離する。iOS / Android実機でWebViewの描画、音声、復帰、メモリを検証する。

## 7. 移行の完了条件

- まずホームと恐竜ランをBabylon.jsで動かし、既存の操作・記録・ゲームへの導線を確認する。
- 恐竜のゲーム世界を3D化し、固定カメラでもジャンプ先と障害物が判別できる。
- ステージを繰り返し開始・終了してもCanvas、イベント、音声、GPUリソースが増え続けない。
- 音楽同期と当たり判定を描画速度から分離し、既存の決定論的な検証を維持する。
- PCとモバイル実機で性能を計測し、品質設定を調整する。
- 移行が完了した機能からThree.js / Phaser依存を外し、参照がなくなった時点でパッケージを削除する。
- 残る10ゲームはそれぞれ短い1ステージで操作・勝敗・リトライを検証してから増やす。
