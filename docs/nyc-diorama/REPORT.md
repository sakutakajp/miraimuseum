比較ページ: `/lab/nyc-diorama`。ユーザー提供の画像だけを使用し、元画像・Camera Projection・2.5D Parallaxを切り替えられる。実際の画像切り抜きと行列による投影を実装済み。Blender、APIキー、有料APIは不要。

## 2. それぞれの方式

**A: Camera Projection** は10×10の正方形Box台座と、輪郭に合わせた閉じた押し出し形状を使用する。主要ビルは地面線の角でファサードを折り、段差・尖塔を含む輪郭に厚みを与える。水面は水平ジオメトリ、橋は橋脚・桁・ケーブルの透過形状。固定投影カメラのView/Projection行列からUVを求め、実画像のクロップを投影する。投影方向から外れる面は近似色へ切り替え、不自然な伸びを抑える。画像の不完全な平行投影に合わせた小さなレンズ補正を共通で使用する。

これは単一視点から推定したファサードの立体モデルであり、実測の完全な3D都市ではない。屋上・裏面の建築詳細は復元していない。96メッシュ、2,235三角形。

**B: 2.5D Parallax** は台座、川、後景ビル、中景ビル、ESB、WTC、前景ビル、公園・樹木、港、橋、船、タクシーの12枚。元画像の画素位置を基準カメラの光線上に配置し、各カードに独立した奥行きを与えた。カードはビューアーへ追従するビルボードにはしていない。`parallax.depthScale = 0.38`で動かしたときの隙間を抑える。

手動ポリゴン・橋ケーブル座標はJSONで管理し、Pythonで透過PNGを再生成する。空の色と橋の暖色判定で細線を補助。前景を下地に重複させず、穴は周囲の元画像の画素で補完する。12メッシュ、24三角形。

## 3. 元画像への再現度

基準視点では両方式とも高い。建築の窓、素材感、公園の緑、黄色いタクシー、川と船、日中の光を元画像から保持した。元画像自体に含まれる陰影を使用し、追加照明で写真の印象を変えていない。

背景は元画像の空色に合わせた滑らかな色面と接地影の残差を使用する。色のわずかな違い、切り抜き境界、一部の橋ケーブルの抜けは残る。再合成と画面キャプチャの平均絶対差は`asset-metrics.json`、`comparison-metrics.json`に記録。RGB誤差は細線や影の美しさを保証する評価率ではないため、同角度の画像も併せて確認する。

## 4. カメラ移動時に残る破綻

| A | B |
| --- | --- |
| 隠れていた面は単色に近く、屋上・ファサードの厚みは概略。草木は球形の完全な立体ではない | 建物は平面で、足元が下地に対して少し滑る。回転でカードの傾きが見える |
| 接地影は画像由来で、回転に合わせた物理的な影にはならない | 公園・建物の背後に、補完した下地のぼけが見える場合がある |
| 大きな角度で切り抜きの不足、細い橋部材の継ぎ目が見える | 水際・橋・木の輪郭で小さな隙間や青い縁が出る場合がある |

標準は左右±10°・上下±5°。鑑賞用にさらに破綻を抑えるなら左右±6°・上下±3°を推奨。UIから最大左右±20°・上下±10°まで調整できる。

## 5. スマートフォン

390×844、DPR 3、タッチ有効のChromiumで、ドラッグ、ピンチ、キャンセル、リセットと横にはみ出さない表示を検証。CSS 358pxの鑑賞領域は483×483で描画し、DPRを1.35に制限する。RGBA換算のテクスチャは約20MiB、ミップマップ込み概算約27MiB。Canvasやドライバのメモリは別。

画像は最大1254px、両方式でテクスチャを共用。元画像モードでは描画停止、静止時は連続描画せず、非表示タブでも停止する。Engine・Scene・イベント・ResizeObserver・RAFを破棄する。合計の画像・設定転送は約5.4MBなので、展示への採用前に圧縮と読込分離を改善する余地がある。

**実際のiPhone・AndroidでのFPS、発熱、メモリ上限、Safari/WebView動作は未測定。** ブラウザの端末エミュレーションを実機性能とは扱わない。

## 6. 長所・短所

| 方式 | 長所 | 短所 |
| --- | --- | --- |
| A | 実ジオメトリの面と厚みを感じられる。将来の3Dモデルへつなげやすい | 単一画像のモデル推定と投影の調整が必要。未撮影面・屋上の品質が制約 |
| B | 元画像の外観を維持しやすい。モデリング不要、少ないメッシュで軽い | 移動範囲が小さい。下地補完、平面感、足元のずれに注意 |

## 7. みらい博物館への採用判断

**美しい箱庭を小さな視点変化で鑑賞する展示にはBを優先する。** 基準画像の魅力を保ち、12メッシュで構成できる。まず可動範囲を控えめにして、実機と拡大表示で境界を確認して採用する。

自由な回り込みや大きな視点変更を展示仕様に含める場合は、Aを基盤として屋上・裏面・橋を補う。今回の画像だけで全方向の建築模型品質を得られたとは評価しない。

## 8. 次に改善すること

1. 橋ケーブル、樹木、ビルの接地部分のマスクを画素単位で調整する。
2. 隠れた道路・草地の下地を手作業で補い、色のぼけを減らす。
3. Bの奥行き・最大角度を実機上で決める。PNGを保持しつつ配信用画像の圧縮を検討する。
4. Aに簡単な水平屋上面と裏面の窓色を追加し、回転で見える面を整える。
5. 低価格Android・iPhone SafariでFPS・発熱・復帰・メモリを測る。

## 検証結果

最新の`work`構成で`npm run typecheck`、`npm test`（既存9件）、`npm run build`を通過。`npm run test:nyc`の新規ブラウザ3ケースも通過し、操作・角度共有・名称・重ね合わせ・描画停止・再試行・離脱を確認した。既存ローマ箱庭のGLB読み込み失敗時の表示テストも通過。開始時点の旧構成では既存117件のユニットテストを通過していた。

ローマ箱庭の全操作E2EはThreeの操作ケースが長時間化したため中断し、その実行では残り6ケースを実施していない。全既存E2Eの通過は確認できていない。既存ホーム・ローマ箱庭・素材の実行ロジックは変更しておらず、この実験の3Dロードは比較ページ内に限定している。比較スクリーンショットは最新構成でも再撮影し、基準視点の画像が同一であることを確認した。

比較画像は`comparison.png`。各方式の基準視点と左右+8°・上下+3°・ズーム1の個別PNG、PC画面、DPR 3のモバイル相当画面も保存している。再撮影は素材READMEのコマンドを参照。
